# Номерной фонд: добавление и удаление номеров пачкой

Дата: 28.10.2026. Ветка: `feature/rooms-bulk`.

## Зачем

Просьба гостиницы: «вношу вручную по 40 и больше номеров — нужно добавлять сразу
много; и чтобы можно было удалять сразу несколько». Сейчас в разделе «Номерной
фонд» номер заводится и удаляется только по одному.

На сервере создание пачкой уже есть (`POST /rooms/bulk`, пункт Д2 сравнения со
старой системой), но в интерфейсе его не вызывает никто. Удаления пачкой нет
нигде.

## Рамки

Входит — только раздел «Номерной фонд» кабинета гостиницы (Kars Hotel PMS):

1. Добавить номера одной категории пачкой: «с номера N, столько-то штук».
2. Удалить несколько номеров разом — так же «в архив», как одиночное удаление
   (решение владельца 25.10.2026): номер не стирается и восстанавливается
   кнопкой «Восстановить» в блоке «Удалённые номера».

Не входит:

- Kars Avia v3 — он только читает список номеров из PMS и новых номеров увидит сам;
- физическое удаление (выключено, `room-delete.switch.ts`);
- восстановление пачкой, правка пачкой (категория, этаж, статус), загрузка из Excel;
- пересчёт остатка для продажи при изменении числа номеров — отдельная задача
  сразу после этой (см. «Следом»);
- задачи уборки на удалённых номерах и отказ демо-заполнения при удалённых
  номерах — замечены при разведке, к этой задаче не относятся.

## Решения

| Вопрос | Решение |
|---|---|
| Где заводится пачка | Переключатель «Один номер / Несколько» в том же окне «Добавить номер». Только при создании, в правке номера его нет |
| Как задаётся пачка | «С номера» + «Сколько» (1–200) + необязательные «Префикс» и «Суффикс» — правило сервера `create-many-rooms.dto.ts`. Под полями — живой предпросмотр списка |
| Номер уже существует | Остальные создаются. Итог называет отдельно номера, которые есть в фонде, и номера из удалённых — с подсказкой восстановить. Всё создано — окно закрывается |
| Как выбрать номера для удаления | Режим выбора прямо на сетке карточек: кнопка «Выбрать», галочки на карточках, «Выбрать все в категории», нижняя строка «Выбрано: N · Удалить выбранные» |
| У части номеров действующие брони | Удаляются остальные. Номера с бронями названы в итоге с числом броней и остаются отмеченными |
| Как удаление доходит до сервера | Новая ручка `POST /rooms/archive-many`: один запрос, ответ по каждому номеру, одна запись журнала на пачку |

Почему одна запись журнала: журнал гостиницы виден оператору Kars Avia в истории
гостиницы (последние 50 записей, `connectivity.service.ts:979-995`), и 40 строк
«номер удалён» вытеснили бы всё остальное. Кто и когда удалил каждый номер, и так
записано в самом номере (`archivedBy`, `archivedAt`). Так же уже сделано создание
пачкой (`create_many`).

## Сервер — `backend/src/modules/rooms`

### Создание пачкой (доработка)

- `CreateManyRoomsDto` получает `partnerHold?: RoomPartnerHold` — поле «Договорный
  блок» есть в форме и должно действовать на всю пачку (в одиночном DTO оно есть,
  `create-room.dto.ts:96-98`).
- `createMany` делит уже существующие номера на два списка:
  - `skipped` — номер есть в фонде (`archivedAt` пуст);
  - `skippedArchived` — номер в удалённых.
- Ответ: `{ created, skipped, skippedArchived, rooms }`. Запись журнала
  `create_many` хранит оба списка.
- `skipExisting=false` по-прежнему даёт 409 на любой занятый номер; фронт это поле
  не шлёт.
- Смена смысла `skipped` безопасна: ни фронт PMS, ни Kars Avia ручку `/rooms/bulk`
  сейчас не вызывают.

### Удаление пачкой (новое)

- `ArchiveManyRoomsDto { ids: string[] }` — массив UUID, от 1 до 200
  (`@IsArray @ArrayMinSize(1) @ArrayMaxSize(200) @IsUUID('all', { each: true })`,
  как `super-admin/dto/apply-feature.dto.ts:12-16`).
- `POST /rooms/archive-many`, право `room.update` — то же, что у одиночного
  удаления.
- `RoomsService.archiveMany(ids)`, одна транзакция `forTenant`:
  1. повторы в `ids` убираются;
  2. читаются номера по `ids` (чужие гостиницы отсекает `forTenant`);
  3. действующие брони (`LIVE_RESERVATION_STATUSES`: NEW, CONFIRMED, CHECKED_IN)
     считаются по номерам одним `groupBy`;
  4. номера без действующих броней и ещё не удалённые уходят в архив одним
     `updateMany`: `isActive=false`, `archivedAt`, `archivedBy`.
- Ответ:

  ```ts
  {
    archived: { id: string; number: string }[];   // удалены сейчас или были удалены раньше
    blocked: { id: string; number: string; liveReservations: number }[];
    notFound: string[];                            // id, которых нет в этой гостинице
  }
  ```

  Повтор безвреден, как у одиночного удаления: уже удалённый номер попадает в
  `archived`, но не меняется и в журнал не пишется.
- Журнал: одна запись `entity='room'`, `action='archive_many'`, `entityId` пустой,
  `diff.after = { archived: [номера], blocked: [номера] }` — только если хоть один
  номер удалён сейчас.
- Одиночные `archive` и `restore` не меняются.

## Фронт — `frontend/src`

### Общее

- `api/rooms.js`: `createRooms(payload)` → `POST /rooms/bulk`,
  `archiveRooms(ids)` → `POST /rooms/archive-many`.
- `hooks/api/useRooms.js`: `useCreateRooms`, `useArchiveRooms` — сбрасывают те же
  ключи `rooms` и `roomTypes`, что одиночные.
- `components/HotelPMS/components/Rooms/room-range.js` — чистые функции, без React:
  - номера диапазона: `prefix + (start + i) + suffix`, как на сервере;
  - строка предпросмотра: до 6 номеров — все через запятую, больше — два первых,
    «…» и последний: «Будут созданы: №101, №102 … №140 (40 номеров)»;
  - склонение «номер / номера / номеров», «бронь / брони / броней»;
  - тексты итогов создания и удаления.
  Рядом — `room-range.test.mjs` (`node --test`).

### Добавление пачкой — `RoomFormModal.jsx`

- При создании сверху переключатель «Один номер / Несколько»; при правке его нет.
- В режиме «Несколько» поле «Номер» заменяется полями «С номера», «Сколько»,
  «Префикс», «Суффикс» и строкой предпросмотра. Остальные поля общие и при
  переключении не сбрасываются.
- Проверки до отправки: «С номера» — целое ≥ 0, «Сколько» — целое 1–200. Пока
  поля неверны, предпросмотра нет, ошибка видна у поля.
- Итог:
  - всё создано — окно закрывается;
  - что-то пропущено — окно остаётся открытым и показывает итог, кнопка
    становится «Готово»:
    «Создано 38 из 40. Уже есть в фонде: №101, №102. В удалённых: №105 —
    восстановите его в блоке «Удалённые номера» внизу страницы»;
  - ничего не создано — тот же итог, начиная с «Ничего не создано».
- Ошибку сервера окно показывает так же, как сейчас при одиночном создании.

### Удаление пачкой — `Rooms.jsx`

- `Rooms/useRoomSelection.js` — хук выбора: набор id, отметить/снять номер,
  отметить/снять категорию, очистить. Механика как в админ-панели
  (`AdminPanel.jsx`): набор id, «выбрать все», строка «Выбрано: N».
- `Rooms/SelectionBar.jsx` — нижняя строка «Выбрано: N · Удалить выбранные ·
  Отмена» и строка итога.
- Кнопка «Выбрать» в шапке (видна, когда есть хотя бы один номер). В режиме выбора:
  - нажатие на карточку ставит или снимает галочку, окно номера не открывается;
  - на карточке — настоящий `<input type="checkbox">` с подписью номера (его
    состояние пишет журнал действий), отмеченная карточка выделена рамкой;
  - значок уборки не открывает меню; «+» в сетке, «Категория», «Добавить номер» и
    кнопки правки/удаления категории скрыты; вместо «Выбрать» — «Отменить выбор»;
  - в шапке категории — «Выбрать все в категории» / «Снять все».
- «Удалить выбранные» открывает общий `ConfirmDialog`: «Удалить N номеров?»,
  перечень номеров (до 10, дальше «и ещё K») и то же объяснение про архив и
  брони, что у одиночного удаления. Сбой запроса целиком диалог показывает сам.
- После ответа:
  - удалённые и ненайденные номера снимаются с выбора;
  - номера с бронями остаются отмеченными, итог в нижней строке: «Удалено 38 из
    40. Не удалены: №105 — 2 действующие брони, №112 — 1 действующая бронь.
    Перенесите брони на другие номера и удалите их»;
  - удалено всё — режим выбора закрывается.

## Проверка

- Серверные спеки в стиле `room-archive.spec.ts` (замоканный `tx`, формулировки
  отрицанием), каждая проверена мутацией — сломать поведение и убедиться, что
  тест падает:
  - номер с действующей бронью НЕ удаляется, остальные удаляются;
  - на пачку НЕ пишется по записи журнала на номер — одна `archive_many`;
  - уже удалённый номер НЕ меняется и НЕ попадает в журнал повторно;
  - больше 200 id и не-UUID НЕ принимаются;
  - удалённый номер при создании пачкой НЕ попадает в `skipped` — он в
    `skippedArchived`;
  - договорный блок пачки НЕ теряется.
- `room-range.test.mjs` — диапазон с префиксом и суффиксом, предпросмотр до и
  после 6 номеров, склонения, тексты итогов.
- `backend`: `npm run build`, `npx jest src/modules/rooms`.
  `frontend`: `npm run lint`, `npm test`, `npm run build`.
- Живой прогон на стенде — владелец.

## Следом — отдельная задача

Остаток для продажи (`inventory`) не следит за числом номеров: строка дня
создаётся с числом номеров на тот момент и потом не меняется
(`inventory.service.ts:111-131`). Новые номера не продаются на даты, где строка
уже есть; удалённые там продолжают считаться.

Рядом, по коду, — более серьёзный дефект: «Доходность» сохраняет закрытые номера
и стоп-продажу без числа номеров (`Revenue.jsx:247`), а сервер подставляет 0 и
записывает его в строку (`inventory.service.ts:304-323`) — после правки дня в
«Доходности» день продаётся с нулевым остатком. Вживую не проверено.

Обе вещи упираются в одно решение — что значит число в строке остатка: сколько
номеров есть физически или сколько гостиница решила продавать.

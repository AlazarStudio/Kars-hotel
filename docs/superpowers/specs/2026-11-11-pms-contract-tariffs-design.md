# Корпоративный тариф ПМС из реестра договоров Kars Avia — дизайн

Дата: 11.11.2026. Согласовано с Мусой по разделам (1 — данные и правило цены,
2 — экраны, 3 — Авиа/миграция/проверка).

Репозитории: **Kars Hotel PMS** (`C:/dev/Kars-hotel`, ветка `codex/mussa`) — вся
работа; **Kars Avia v3** (`C:/dev/kars-avia-v3`, ветка `codex/mussa`) — одна
точка отправки. Связь только по HTTP/REST.

## Задача

Привести вкладку «Тарифы» в порядок и сделать так, чтобы корпоративный тариф
гостиницы брал цены из реестра договоров Авии: у «Апартаментов сети Карс Авиа»
27 договоров и ни одного приложения, ещё у 7 гостиниц «Цены по договору» пусто,
подтвердить тариф нельзя (409 «Нет ценового приложения договора — сверять не с
чем»). Плашка «Как завести тариф по договору» ссылается на кнопку, которой при
пустых ценах не существует; пустой экран показывает два пустых блока подряд;
блок «Цены по договору с партнёром» — одна фраза без структуры.

## Решения

1. **Реестр договоров Авии — мастер цен.** Из ПМС цены в реестр не пишутся.
   Гостиница не вводит цены корпоративного тарифа: он их берёт из договора.
2. **Авиа дополняет существующую синхронизацию списком договоров** (не только
   приложениями с ценами) — иначе «договор есть, цен нет» показать нечем.
   В ПМС появляется таблица `partner_contract` (миграция).
3. **Цена корпоративного тарифа читается из зеркала договора на лету**, а не
   копируется в тариф: расхождение с договором невозможно по построению, новая
   ДС действует сама.
4. **Сверка тарифа оператором больше не нужна**: цены и условия берутся из
   реестра, сверять нечего. Статусы `DRAFT/CONFIRMED/REJECTED/STALE` уходят с
   экрана. Экран сверки в Авии в этой задаче не трогаем — его удаление отдельно.
5. **Экран корпоративного тарифа** — «Цены договора» (таблица на период) и
   «Календарь» (цена каждой ночи), оба только чтение. Своих сезонов и календаря-
   редактора у такого тарифа нет; у обычных тарифов гостиницы всё как было.
6. **Плашки-инструкции нет.** Её содержание — это шаги мастера «Новый тариф»,
   как в окнах-мастерах Авии: степпер, «Далее» не пускает незаполненный шаг.

## 1. Что приезжает из Авии

`PUT /api/connect/v1/hotels/:slug/contract-prices/sync` сегодня принимает
`{ documents: ConnectContractPricesDto[] }`. Добавляется необязательное поле:

```
contracts?: [{
  number: string,                  // номер договора как в реестре
  account?: { code, name },        // юрлицо Карс (karsCompany), как в pricedoc.account
  signedAt?: ISO | null,           // срок договора
  expiresAt?: ISO | null,
  isPrimary: boolean,              // рабочий договор гостиницы
  state: 'ACTIVE' | 'ARCHIVED',    // скрытые не отправляются вовсе
  services: ('ACCOMMODATION' | 'MEAL')[],
  sheets: number                   // сколько документов этого договора в наборе; 0 — цен нет
}]
```

Правила отбора в Авии: те же, что у документов — договор покрывает эту гостиницу
(своя отметка или `alsoHotels`). Скрытый договор (`hiddenAt`) не отправляется;
архивный — отправляется со `state: 'ARCHIVED'`. `sheets` считается по уже
собранному набору документов, отдельного запроса нет.

**Семантика набора** — как у документов: присланное заменяет прежний список
этого партнёра целиком; чего в наборе нет — того в ПМС нет. Поле не пришло
(старая Авиа) — список договоров не трогаем.

## 2. Таблица partner_contract в ПМС

Миграция пишется руками, по образцу `20260829190000_partner_contract_price`.

| колонка | тип | смысл |
| --- | --- | --- |
| `id` | UUID PK | |
| `tenant_id` | UUID NOT NULL → tenant | гостиница |
| `partner_id` | UUID NOT NULL → partner | чей реестр |
| `number` | TEXT NOT NULL | номер договора |
| `account_code`, `account_name` | TEXT | юрлицо Карс снимком |
| `valid_from`, `valid_to` | TIMESTAMP(3) | срок договора |
| `is_primary` | BOOLEAN NOT NULL DEFAULT false | рабочий договор |
| `state` | TEXT NOT NULL | `ACTIVE` / `ARCHIVED` |
| `services` | TEXT[] | какие услуги есть по договору |
| `sheets_count` | INTEGER NOT NULL DEFAULT 0 | сколько приложений пришло |
| `received_at` | TIMESTAMP(3) NOT NULL DEFAULT now() | когда обновлено |

Уникальность `(tenant_id, partner_id, number)`, индекс по `tenant_id`,
RLS-политика `tenant_isolation` — как у `partner_contract_price`.

Синхронизация: поле пришло — `DELETE` строк этого `partner_id` и вставка
присланных в одной транзакции; поле не пришло — ничего.

Представление для экрана — объединение «договоры из реестра ∪ договоры из
приложений»: старая Авиа не присылает реестр, и гостиница не должна терять то,
что уже видит.

## 3. Правило цены корпоративного тарифа

Корпоративный тариф хранит **только условия**: `partnerId`, `operatorContract`,
`partnerAccountId` (юрлицо), `partnerCustomerId` (авиакомпания), `guestKind`,
`mealPlan`. Своих строк цен у него нет.

Цена ночи `d` для категории `rt` и числа гостей `g`:

1. Среди документов договора (`partner_contract_price` этого `tenant` и
   `partnerId`, `contract_number = tarif.operatorContract`, услуга
   `ACCOMMODATION`) собрать все сетки `fill[]`. Номер договора сверяется как
   есть: в реестре и в документах это одно поле Авии (`hotelContract.number`),
   преобразований нет.
2. Взять сетку с самым поздним `from <= d`. Нет такой — **цены нет** (договор
   не покрывает этот день: разрыв между приложениями, истёкший срок). Если у
   тарифа задано юрлицо, годится только сетка от документа этого юрлица —
   цены чужого юрлица не подставляются; документ без юрлица подходит любому.
   Сетка годится, только если её документ покрывает этот день: в разрыве между
   ДС и после окончания договора цены нет.
3. В сетке выбрать срез: `customer` = код авиакомпании тарифа (по
   `partnerCustomerId` из справочника партнёра), иначе (если точного нет) срез
   с `customer = null` — «для любой». `guestKind` и `mealPlan` — только
   точное совпадение: питание и вид брони, которых в договоре нет, не
   подменяются общими. Нет среза или код авиакомпании не найден в справочнике —
   цены нет, причина показывается на экране.
4. Взять ячейку `categoryId = rt`, `occupancy = g`. Нет ячейки (гостей больше
   вместимости, категория не покрыта) — цены нет.

Следствия:

- **Цены не пересчитываются в ПМС своим правилом.** Берутся готовые сетки Авии:
  две копии правила разошлись бы тихо, и разошлись бы в деньгах. Сетки уже
  приезжают сегодня внутри документов (`documents[].fill`); нового поля для них
  не нужно — новое поле нужно только списку договоров.
- Число гостей — строго. Колонки «одна цена» у такого тарифа нет.
- НДС — из документа, действующего на этот день; поле тарифа не участвует.
- Документ без сетки (Авиа не смогла собрать: категории гостиницы не доехали)
  = цены нет. На экране: «Авиа не прислала цены по договору — попросите
  диспетчера обновить»; в Авии для этого есть пересинхронизация одной гостиницы.
- Нет цены хотя бы на одну ночь — тариф на эту бронь не предлагается (как уже
  работает `priceByPlan`: тариф без полной цены отбрасывается).
- Ограничения (стоп-продажи, минимальный срок, закрытия) остаются за
  гостиницей: они про номера, а не про цену договора, и работают как у любого
  тарифа.

## 4. Где правило живёт в коде ПМС

Одна функция «цена договора на ночь» в новом модуле
`backend/src/modules/contracts/` (там же приём `partner_contract` из
синхронизации), с кэшем ответа в Redis на короткий срок; кэш сбрасывается при
синхронизации договоров этого партнёра. Её спрашивают:

- `availability.priceByPlan` (`inventory/availability.service.ts`) — цена
  тарифа по ночам, витрина и цена предложения для Авии;
- `PricingService.quote` (`pricing/pricing.service.ts`) — расчёт стоимости;
- `RatePlansService.withOperatorStatus` (`rate-plans/rate-plans.service.ts`) —
  `applies` теперь значит «на нужные ночи есть цена договора», а не «оператор
  подтвердил».

Фильтры в `connectivity.service.ts` (`applying`), которые отбрасывают
неподтверждённые тарифы, остаются — меняется только источник `applies`.
Расчёт обычных тарифов не меняется ни на строку.

Для экрана нужна ещё одна ручка: `GET /rate-plans/:id/contract-prices`
(право `rate.read`, как у тарифов) — периоды договора (документы с датами и
номерами ДС) и сетка выбранного периода по категориям и числу гостей. Считает
её та же функция, поэтому экран и расчёт не могут разойтись. Клиентское правило раскладки цен (`fillGrid`, `sliceCells`
в `components/Tariffs/corporateTariff.js`) удаляется; остаются только подписи
условий и срезов (`sliceName`, `partnerConditions`, `planForSlice` для блока
«Завести тариф»).

## 5. Экраны

### 5.1 Мастер «Новый тариф»

Одно окно с этапами; степпер в шапке, «Далее» не пускает незаполненный шаг,
внизу Назад · Отмена · Далее. Шаги зависят от первого ответа.

- **Свой тариф гостиницы:** Для кого → Питание → Цены → Сезоны → Проверка.
  Тариф создаётся на последнем шаге, цены и сезоны сохраняются сразу после
  создания. Не сохранилось — окно остаётся на нужном шаге и говорит, что не
  легло. Второго окна (`PlanWizard`) нет.
- **Корпоративный:** Для кого → Договор → Срез → Проверка.
  - «Договор» — список из реестра, включая договоры без цен; у такого пункта
    пометка «цен нет». Выбрать можно: тариф появится в списке с состоянием
    «Ждёт цен по договору» и начнёт работать сам, когда приложение приедет.
    Запирать создание значило бы показать 27 договоров и не дать ничего с ними
    сделать.
  - «Срез» — юрлицо, авиакомпания, вид брони, питание. Предлагаются значения,
    которые в договоре действительно есть (из сеток), плюс «любая/любой».
    Питание, которого в договоре нет, не предлагается — тариф был бы заведомо
    пустым.
  - «Проверка» — что увидит Авиа: категории с ценами договора, чего в договоре
    нет, с какого числа действуют цены.

Кнопка **«Завести тариф»** у среза в блоке «Цены по договору» открывает тот же
мастер с уже выбранными договором и срезом.

Правка корпоративного тарифа — та же форма условий без полей цен: смена
договора или среза сразу меняет цены, потому что они не хранятся.

### 5.2 Экран корпоративного тарифа

Вместо «Базовые цены / Сезоны / Календарь» — два подтаба, оба только чтение:

- **«Цены договора»** — таблица «категория × число гостей» на выбранный
  период; переключатель периода — договор и каждая ДС («с 10.11.2025»).
  Под таблицей: для каких категорий цены в договоре нет.
- **«Календарь»** — цена каждой ночи из сеток; полосами видно, с какого числа
  действует новая ДС; даты вне договора помечены «вне договора» и ценой не
  заполнены.

Состояние тарифа — «работает» / «Ждёт цен по договору»: считается по цене
договора на сегодня, не хранится. У обычного тарифа всё как сейчас, с
редактированием.

### 5.3 Блок «Цены по договору с партнёром»

Карточка на договор: номер, юрлицо, срок, «приложений: N», рабочий/архив.
Договор без цен виден с честной строкой «цен нет — приложение не пришло». Для
договора с ценами — срезы с ценами и кнопка «Завести тариф» у среза.

### 5.4 Пустые состояния

Нет тарифов и нет договоров — один пустой экран (сейчас два блока подряд).
Нет тарифов, но договоры есть — пустой экран говорит «тарифы заводятся из
договоров ниже»; блок договоров уже стоит под ним.

### 5.5 Что убираем

`PartnerTariffGuide` и ключ `pms.tariffGuide.closed`; статусный баннер сверки у
корпоративного тарифа; цветные точки статусов на ярлыках тарифов; кнопки
«Заполнить по договору» и «Сезоны по договору»; у корпоративного тарифа —
поля цены питания, наценок и НДС (питание задано срезом, НДС приходит из
документа); клиентская раскладка цен (`fillGrid`, `sliceCells`) — цена теперь
одна, серверная.

## 6. Уже заведённые корпоративные тарифы и сверка

- Прежние цены (базовые, сезоны, цены дня) остаются в БД, в расчёт не идут.
  Экран сразу показывает цены договора.
- `reviewVerdict`, `reviewFingerprint`, `reviewNotes` остаются как история;
  чтение вердикта убирается.
- `applyOperatorReview` продолжает отвечать 200 и писать историю — старая Авиа
  не должна получить 404/409. Отпечаток считается по документам и условиям
  (без цен тарифа), поэтому экран сверки в Авии продолжит работать, хотя ни на
  что не влияет.
- Удаление сверки в Авии — отдельная задача.

## 7. Совместимость и порядок выпуска

У ПМС включён `forbidNonWhitelisted` — новое поле в старом ПМС дало бы 400 на
всей синхронизации. Поэтому **сперва ПМС, потом Авиа**. Пока Авиа не обновлена,
ПМС работает как сегодня (договоры берутся из приложений). Откат Авии безопасен:
поле просто перестанет приходить.

## 8. Проверка

- ПМС, бэкенд: `pnpm exec prisma generate`, `pnpm run build`; целевые
  Jest-тесты — новый спек правила «цена договора на ночь» (срез, период,
  разрыв, число гостей, «для любой авиакомпании», чужое юрлицо), спек
  синхронизации (полная замена, отсутствие поля), правленые спеки статуса.
- ПМС, фронт: `pnpm run lint`, `pnpm run build`.
- Авиа: `tsc --build tsconfig.json --emitDeclarationOnly` в `libs/identity`,
  тест зеркала (в наборе уходит `contracts`).
- Миграция к локальной базе — только по отдельному слову Мусы.
- Браузер и ручную приёмку делает Муса. На локальном стенде одна тестовая
  гостиница: договоров у неё может не быть, и пустой реестр — правда.

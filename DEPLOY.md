# Развёртывание Kars Hotel PMS

PMS живёт на **своём VPS**, отдельно от Kars Avia. Системы разные, и общая
машина означала бы, что падение одной уносит другую. Связь между ними — только
по HTTP, партнёрским ключом.

## Первый запуск

```bash
git clone <репозиторий> && cd Kars-hotel
cp .env.example .env      # домен, пароль базы, секрет токенов
docker compose up -d --build
docker compose exec api pnpm exec prisma migrate deploy
```

Перед этим: записи A/AAAA домена смотрят на этот VPS, порты 80 и 443 открыты.
Без этого Caddy не пройдёт ACME-проверку и сертификата не будет.

## Что где

| Служба | Роль | Наружу |
|---|---|---|
| `caddy` | TLS и маршрутизация | 80, 443 |
| `web` | кабинет (статика) | нет |
| `api` | NestJS, `/api/*` | нет |
| `postgres`, `redis` | данные | нет |
| `backup` | суточные копии | нет |

Кабинет и API на ОДНОМ домене: адрес API в сборке фронта относительный
(`/api`), поэтому смена домена не требует пересборки.

## Резервные копии

Служба `backup` снимает дамп базы раз в сутки (по умолчанию 03:00 UTC), хранит
14 дней и складывает в том `backups` на этом же сервере.

```bash
docker compose logs backup            # что и когда снималось
docker compose run --rm backup /backup/restore.sh          # список копий
docker compose run --rm -e CONFIRM=yes backup \
  /backup/restore.sh pms-2026-09-02_0300.dump              # восстановить
```

**Проверьте восстановление до того, как оно понадобится.** Копия, которую ни
разу не разворачивали, — не копия, а надежда. Разверните её в отдельную базу и
сравните счётчики хотя бы раз.

Версия образа `backup` обязана совпадать по мажору с образом базы: `pg_dump`
более старой версии откажется снимать дамп с более нового сервера, служба будет
писать ошибку в журнал, а копий не будет. Ровно так и вышло при проверке
02.09.2026 на соседнем проекте.
